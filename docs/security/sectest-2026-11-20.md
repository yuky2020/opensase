## How to run

```sh
deploy/dev/bootstrap.sh            # stack up (only if it is not running)
make sectest                       # black box (test/security/*.sh) + Go (test/security/go)
make sectest-unit                  # Go checks without a stack
SECTEST_DESTRUCTIVE=1 make sectest # also the loopback flood
```

`test/security/README.md` covers subsets, layout and conventions. Each Go run creates fresh
tenants named `sectest-<run>-a|b`, and revokes every identity it created when it ends. The API
has no tenant deletion, so the empty tenants remain.

A PASS always comes with a positive control. A refusal counts only when the same harness has
shown that it can see the success case. Examples:
- a ping answered through the tunnel;
- a SYN-ACK from example.com;
- the refused identity working on its own route;
- the untampered cache being loaded.

Data-plane refusals require an explicit RST from the Edge filter; silence is not enough. One run
caught a check that passed for the wrong reason. Those checks now accept only an explicit 403.

## Findings

### ST-01 (Medium): the Edge does not check certificate serials, so superseded or never-issued device certificates open tunnels

- **Reproduction:** `SEC-AUTH-031` and `SEC-TLS-012`.
- **What happens:**
  - After `POST /v1/renew`, the Control Plane refuses the old certificate everywhere except
    `/v1/renew` (SEC-AUTH-030 passes).
  - The Edge session channel still accepts it: HTTP 200, a WireGuard peer, a tunnel IP.
  - A certificate that the CP never issued is also accepted, provided it is signed by the right
    tenant CA and carries a real device ID. The CP answers it with 403 (serial check), the Edge
    with 200.
- **Cause:** the Edge authenticates with chain and SPIFFE ID only (`internal/edge/session.go`
  `handleSession`). `api.EdgeDevice` carries no serial.
- **Impact:**
  - A stolen device key and certificate keeps full tunnel access after the owner renews, until
    `NotAfter` (up to 24 h). The point of the serial swap (review #4) is lost on the data plane.
  - Revocation still works (SEC-AUTH-020).
- **Fix:**
  - Add `CertSerial` to `api.EdgeDevice`. This is a contract change, so the lead must approve
    it.
  - Refuse `/v1/session` when `leaf.SerialNumber` differs.
  - At peer sync, remove the WireGuard peers whose session was set up with a serial that is no
    longer current.

### ST-02 (Medium): a superseded certificate can renew again, which takes the device over and locks the owner out

- **Reproduction:** `SEC-AUTH-032`.
- **What happens:**
  1. The device renews (cert N becomes N+1), then uses N+1 successfully.
  2. A holder of the old certificate N calls `/v1/renew`. The CP accepts it as a "lost
     response" retry (`store.renewCert`, branch `presented == prev`).
  3. The CP issues N+2 and makes it current. The owner's N+1 now gets 403.
  4. The attacker then keeps renewing with N+2 indefinitely.
- **Impact:** a stolen superseded key, which the device has just rotated away from, becomes a
  persistent identity, and the real device is locked out. The same code path serves connectors
  (`RenewConnectorCert`).
- **Fix:** accept the previous serial only until the current certificate is first used. Clear
  `prev_cert_serial` in `authDevice`/`authConnector` when the current serial authenticates on
  any route. A short retry window (for example 5 min after the renewal) is a cheap extra bound.

### ST-03 (Medium, design): one global admin token, no tenant-scoped administration

- **Reproduction:** `SEC-TEN-020`.
- **What happens:** the only admin credential reads and writes every tenant's devices, flows,
  policy and connectors. It can also register Private Edges for any tenant.
  "Tenant A's admin" and "tenant B's admin" are the same principal. There is no audit trail of
  admin actions per actor.
- **Impact:** in the SaaS model, any leak of a customer-facing admin credential compromises all
  tenants. Tenant isolation holds only for devices, connectors and Edges (all SEC-TEN checks
  pass).
- **Fix:**
  - Add tenant-scoped admin tokens (or OIDC with a tenant claim), checked in `tenantParam`
    against the `{t}` path parameter.
  - Keep a separate provider super-admin for `/tenants` and `/edges`.
  - Log the admin principal on every write.

### ST-05 (Medium): no rate limit on device and connector enrollment (open item confirmed)

- **Reproduction:** `SEC-IN-008`.
- **What happens:** 150 wrong provisioning keys took about 0.2 s, alternating `/v1/enroll` and
  `/v1/connector/enroll`. All got 403; none got 429.
- **Impact:**
  - Guessing a 256-bit key is infeasible.
  - The real risks are unthrottled CPU and DB work (each valid-prefix attempt runs a store
    transaction) and log flooding (one WARN per attempt).
  - A leaked key that was partially redacted, or a short custom key, would be brute-forceable.
- **Fix:**
  - Per-source-IP token bucket on both enroll routes (for example 10/min, burst 20), plus a
    global cap. Answer 429 with `Retry-After`.
  - Rate-limit the "enrollment rejected" log.

### ST-04 (Low): the Edge broker does not check connector certificate serials

- **Reproduction:** `SEC-TLS-011`.
- **What happens:** the broker accepts a connector certificate for a real connector ID with a
  serial that the CP never issued. It is signed by the tenant CA. The CP refuses it with 403.
- **Impact:** forging the certificate needs the tenant CA key, which only the CP holds. Superseded
  connector certificates also stay usable on the broker until `NotAfter`.
- **Fix:** same as ST-01. Add a serial to `api.EdgeConnector` and check it in
  `connectorAllowed` and at peer sync.

### ST-06 (Low, accepted in ADR-0014): snapshot signing keys are taken from the offline cache itself

- **Reproduction:** `SEC-OFF-005`.
- **What happens:**
  1. The harness replaces `bundle.snapshotKeys` in `state.json` with its own Ed25519 key.
  2. It re-signs every snapshot without rules.
  3. A Private Edge started offline enforces all 28 of them.
- **Why it is accepted:** tenant CAs are anchored to the read-only `/pki/root.crt`; snapshot
  keys are not anchored to anything. ADR-0014 argues that a writer of the state dir can also read
  the Edge key.
- **Why it still matters:** in the dev deployment, `edge-state` is a separate read-write mount
  and `pki/edge` is mounted read-only. A bug that allows a file write in the state dir (flow log
  rotation, a path bug) would become a policy bypass.
- **Fix:** pin the snapshot public key(s) in `pki/edge/` (for example `snapshot.pub`, written by
  `pki init`). Verify cached and live snapshots only against pinned keys, and rotate keys through
  the pinned file.

### ST-07 (Low): a relabelled cache is not re-scoped to the Private Edge's tenant

- **Reproduction:** `SEC-OFF-004`.
- **What happens:** the harness takes a public Edge's `state.json` (28 devices of several
  tenants) and changes `"tenant"` to tenant A. An Edge started with `-tenant A` loads all 28
  devices. Only 9 belong to tenant A.
- **Cause:** `loadState` calls `applyState(st.Peers)` without `scopePeers`, unlike the live
  sync.
- **Impact:** other tenants' devices still cannot authenticate, because `parseBundle` keeps only
  tenant A's CA. This is a lost defence-in-depth layer, not a bypass.
- **Fix:** in `loadState`, apply `e.scopePeers(st.Peers)` before `applyState`.

### ST-08 (Low): Control Plane container has no cap_drop and no no-new-privileges

- **Reproduction:** `SEC-DEP-004`.
- **What happens:** `controlplane` runs as uid 1000, so its effective capabilities are 0. Its
  bounding set is still the docker default (`CapBnd=00000000a80425fb`), and `NoNewPrivs=0`. The
  Edge, Connector and intranet containers set both.
- **Fix:** in `deploy/dev/docker-compose.yml`, `controlplane`, add:
  - `cap_drop: [ALL]`;
  - `security_opt: [no-new-privileges:true]`;
  - ideally `read_only: true`, since its writes go to `/data` and `/pki/tenants`.

### ST-09 (Low): Control Plane database is world-readable on the host

- **Reproduction:** `SEC-DEP-011`.
- **What happens:** `deploy/dev/data` is 0755. `controlplane.db`, `-wal` and `-shm` are 0644.
- **Impact:** every local user can read all tenants' flow records (destinations and domains per
  device, effectively browsing history), policies, the device inventory and provisioning-key
  hashes.
- **Fix:**
  - `bootstrap.sh`: `mkdir -p data && chmod 700 data`.
  - The CP should create the DB with mode 0600 (`umask 077` at startup, or chmod after open).
    This also covers the SQLite side files.

## Other observations (no finding ID)

- **User IDs are global across tenants.** Creating user `user-a` in a second tenant gives 409
  "user exists", which reveals that the ID exists elsewhere. With one global admin (ST-03) this
  is moot. With tenant-scoped admins it becomes a cross-tenant oracle: scope the uniqueness to
  `(tenant_id, id)`.
- **No API to delete a tenant.** The suite cannot clean up fully. A cleanup endpoint (or
  `opensasectl tenant delete`) would help tests and GDPR requests.
- **A JSON `null` body on `PUT /v1/admin/tenants/{t}/policy` is accepted (204).** It decodes as
  `{}` and replaces the tenant policy with an empty `defaultAction: allow` policy. This is valid
  JSON and needs the admin token, but an explicit "empty policy" confirmation or a 400 on
  `null` would prevent accidents.
- **SEC-DP-107 (port outside a private app, through the real client) was skipped.** The dev
  Connector was revoked by `e2e.sh`. The Edge-side ZTNA checks (SEC-DP-008) do not need a
  Connector and pass.

## Summary for the lead

- **96 checks: 85 PASS, 0 FAIL, 10 KNOWN-FAIL (9 findings), 1 SKIP.**
- The core holds:
  - PQ-only TLS on all three listeners;
  - certificate role isolation on every route;
  - forged, foreign-root, expired and wrong-URI certificates are refused;
  - revocation of devices, connectors and Edges;
  - tenant isolation of snapshots, decisions, flows, user rules, connector configs and the
    Private Edge feed;
  - the Edge data plane against a hostile WireGuard client (metadata, private ranges, DNS
    bypass, spoofed sources, device-to-device, ZTNA cross-tenant, IPv6);
  - tampered or corrupt offline caches.
- Top findings:
  1. **ST-01 / ST-04:** the Edge ignores certificate serials, so a superseded or never-issued
     device certificate still opens a tunnel.
  2. **ST-02:** a superseded certificate can renew again, which takes the device over and locks
     the owner out.
  3. **ST-03:** one global admin token for all tenants.
  4. **ST-05:** no enroll rate limit.
- ST-01 and ST-04 need a contract change (`CertSerial` in `api.EdgeDevice` / `api.EdgeConnector`).
- The Low findings ST-07, ST-08 and ST-09 are one-line fixes.
